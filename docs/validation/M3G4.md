## Implemented boundary

PlayerCommandMovementV1 uses the existing genuine MT_PLAYER=0, player/mo binding,
actor storage, execution scope and game-instance provenance. It adds turning,
forward/side thrust and the source reaction-time conditional before the shared
thinker pass. Existing weapon execution shares the extracted checked motion/gate;
there is no second physics engine, scheduler, command format, player timer or
persistent identity/health copy. LifeHost performs immediate RUN entry; existing
XY/friction/sliding and stop entry consume actual commands. Source damage momentum
accumulates with command thrust. Death retains its allocated moving corpse.

Policy4/context selection preserves old body/knockback capabilities and DSIM20/21/22
bytes. Existing fields and Player event describe the new behavior; no new DSIM
version is needed. No actor/geometry capacity changes or automatic AI/roster exist.

## Rust safety and API observations

Thirteen integration policy tests and three private tests pass separately from the
C reference comparison. They cover unsupported settings/geometry/roles, command
ranges/buttons/slots, bounded initial delay, binding/generation/lifetime rejection,
foreign game instances, direct state/physics guards, dead/corpse and inactive input,
complete late postcondition rollback and command-before-think ordering. Existing
scope/provenance compile-fail tests apply to unchanged ownership types.

Every source sequence compares complete step output with advance then snapshot,
followed by 100 zero-command continuation tics per case. Paused and rejected paths
also preserve full authoritative state. A private capture hook observes zero
implicit advance captures for success/pause/error, and one for step. The late
travel-bound rejection test preserves original standing state, angle, momentum,
reaction, RNG, commands and both event queues. These bounded support guarantees
are Rust policy, not original-C error behavior.

## Bounded fuzzing and sanitizers

All 30 targets built with nightly address instrumentation. Five distinct targets
completed 4,096 executions each, 20,480 total, without crashes/assertion/sanitizer
findings. Each used seed 1, timeout 20 s, RSS limit 2,048 MiB and
ASAN_OPTIONS=detect_leaks=0. No LeakSanitizer or exhaustive-safety claim follows.

The new model compares step/advance outcomes and complete rejected state across
commands, initial delays, damage, removal, bindings and pause; it also checks
bounded diagnostic round trips and prefix mutations. These are Rust policy/API
checks, not a C oracle. Separate unit tests corrupt full player associations.
Corpus/artifacts remain outside tracked historical seeds. Actual input budgets,
observed limits, commands and log hashes are retained in the safety JSON. C strict
and ASan/UBSan trace equality is separate evidence; its intentional signed-shift
probe diagnoses the undefined source expression without providing gameplay data.

## Unsupported behavior and next prerequisite

Full PlayerThink/DeathThink, view/camera/bob, weapons/buttons, powers/cheats/armor,
inventory, special sectors, airborne controls, general geometry, active-player
roster, automatic Demon acquisition, respawn/multiplayer and rendering remain
outside this capability. Shared-host timing and bounded fuzzing cannot establish
universal performance or exhaustive safety. The next narrow gameplay milestone
should independently admit active-player roster and original Demon acquisition
through the existing shared simulation.
